日期：2026-11-07（北京时间）。开发分支：`codex/backend-data-20261107`。基线为 `795bb8d`；此前复查中确认的问题已在本轮处理。

## 交付

1. 明确首期边界：免登录浏览，自愿提交游客资料与行程；不引入交易、证件登记、定位追踪和跨设备账号。详见 [范围与数据](SCOPE_AND_DATA.md)。
2. 阅读5份官方原文，新增8条文化资料，保留来源、原文日期、核对日期与出行信息边界。已有12个目的地、3条草稿路线继续保留。
3. 新增SQLite数据库、一次性种子迁移、版本冲突检查、管理操作记录、持久化AI额度、游客与行程关系及在线备份。
4. 实现管理工作台：目的地、路线、文化资料、游客查询／备注／删除／当前页导出、AI设置／测试／问答、账号密码管理。初始管理员使用随机凭证，不设置公开默认密码。
5. 游客网站改为读取数据库公开目录，采用ETag／304、gzip与带提示的缓存回退。后台编辑的发布资料可供游客与助手读取。
6. 新增文化资料页与游客资料页。原“保存行程”继续写当前设备，新增“保存到服务端”由游客主动选择；游客可以删除全部服务端资料及行程。
7. AI服务密钥仅在服务端使用并加密保存；使用已发布审核资料构建上下文，不读取游客资料或维护备注。启动器支持私有配置中的网络代理。
8. 首页地图按需加载；移除首屏控件不需要的整套内嵌图标字体，使用SVG图标；文本静态资源启用缓存后的gzip传输。

## 真实AI检查

本机既有服务配置下，首次直接访问上游失败；使用本机可用代理后，模型列表查询返回200，后台连接检查返回HTTP 200、`mode: ai`，附2个来源，并给出关于铜器制作的简短文化介绍和当前接待待核验说明。

这证明本次配置下的一次真实模型调用可用，不是全面准确率或外部服务长期可用性承诺。模型使用既有别名，实际提供商映射以其记录为准。失败尝试及成功调用均计入本地日额度，没有输出或提交真实密钥。

## 性能对比

对照基线 `795bb8d` 与本轮版本，使用同一套已安装依赖构建，避免把依赖修补本身当作全部性能改善。通过本地生产HTTP服务测量；390×844视口、下载1 Mbps、100 ms延迟、CPU减速4倍，每个版本3个全新浏览器上下文，外部请求被拦截。

| 指标 | 基线 | 本轮 |
| --- | ---: | ---: |
| 主CSS原始构建体积 | 78.35 kB | 32.10 kB |
| 主CSS gzip体积 | 36.92 kB | 7.26 kB |
| 页面实际CSS编码传输总量 | 85,196 B | 8,951 B |
| 页面资源传输总量 | 429,887 B | 248,961 B |
| LCP三次结果 | 3804 / 3804 / 3828 ms | 2476 / 2408 / 2416 ms |
| LCP中位数 | 3804 ms | 2416 ms |

此条件下，资源传输减少约42%，LCP中位数下降约36.5%。新版本增加了一次公开目录请求，页面请求数从9到10；API响应压缩与静态资源压缩减少了实际传输。数值是固定模拟条件下的实验结果，不代表所有真实网络的加载速度。

地图在首页不自动发起第三方SDK请求，点击加载或明确进入地图／路线时再加载。对照基线没有私有配置，因此该对照不用于量化真实高德网络请求的节省；新版本初始无SDK请求已经单独检查。
